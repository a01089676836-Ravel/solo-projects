# EV Factory Lab — 설계 의도와 경험정리

작성 기준: 2026-09-27 실행 결과. 설명의 목적은 ‘어떤 도구를 썼는가’보다 ‘어떤 부족함을 메우고, 어떤 판단을 연습하기 위한 프로젝트인가’를 드러내는 것입니다.

**작성 범위:** 프로젝트 구현과 수치는 파일·실행 기록으로 확인했습니다. 개인의 감정과 깨달음은 확인할 수 없으므로 아래 1인칭 일기는 제안 초안입니다. 본인이 공감하고 실제로 확인한 내용만 자신의 경험으로 사용합니다. 코드는 Codex가 구현·검증을 지원했으며, 사용자가 독자적으로 모든 개발과 실험을 수행했다는 기록은 없습니다.

## 1. 왜 이 프로젝트를 만들었는가

목표는 데이터 분석 공부를 ‘생산 현장에서 무엇을 판단하는 데 쓸 수 있는가’로 연결하는 것입니다. 사용자가 제시한 SDF 데이터 분석과 전동화 생산기술을 한 공정에서 설명할 수 있도록 공통 사례와 두 분석 모듈을 구성했습니다.

- SDF 관점: 공정 기록을 믿을 수 있는가? 제품별 이력이 연결되는가? 어떤 부품을 추가 점검할 것인가?
- 생산기술 관점: 어느 공정에 대기가 쌓이는가? 검사 설비를 늘리는 것과 공정 편차를 줄이는 것은 어떤 차이가 있는가?

두 관점은 ‘데이터를 모으고 예측했다’에서 끝나지 않고 ‘그 결과로 어떤 운영 판단을 할 수 있고, 아직 무엇은 판단할 수 없는가’에서 만납니다.

학습 흐름은 다음과 같습니다.

`직무와 학습 사이의 간극 → 가상 공정 정의 → 제품·공정 데이터 생성 → 데이터 검증 → 위험 분석·병목 분석 → 개선안 실험 → 비용·용량·현실성 검토`

## 2. 대안 중 현재 구조를 선택한 이유

아래는 현재 설계를 설명하는 비교 기준입니다. 모든 대안을 구현해 성능을 실험적으로 비교한 기록은 없습니다.

| 선택지 | 장점 | 이번 목표에 대한 제약 | 현재 선택과 바뀔 조건 |
|---|---|---|---|
| 불량 분류 모델만 만들기 | 기존 머신러닝 학습과 직접 연결, 짧은 기간에 완성 가능 | 설비·대기·개선 의사결정 설명이 부족 | 분류를 SDF 모듈로 두고 공정 실험을 추가. 모델 연구 자체가 목표라면 분류 프로젝트에 집중 가능 |
| 이미지 기반 비전 검사 | 시연이 직관적이며 온디바이스 AI와 연결 가능 | 이번 작업에는 해당 공정의 이미지·정답·촬영 조건이 제공되지 않음 | 현재는 수치형 측정 이력. 적절한 이미지와 검증 환경이 생기면 비전 결과를 제품 ID에 연결 |
| 처음부터 LLM 에이전트 만들기 | 근거 요약·질의응답 등 사용자 경험 확장 가능 | 기본 데이터와 판단 기준이 불명확하면 그럴듯한 설명만 늘어날 수 있음 | 우선 분석 도구와 근거 파일을 고정. 이후 LLM이 이를 호출·인용하는 단계로 확장 |
| 실시간 공장 디지털 트윈 | 실제 운영과 높은 연계 가능성 | 설비 연결, 실제 공정 파라미터, 센서·물류 데이터가 필요 | 현재는 범위를 밝힌 교육용 시뮬레이터. 물리 공장을 검증한 디지털 트윈으로 주장하지 않음 |
| 공개 제조 데이터만 분석 | 외부 데이터에 대한 분석 역량을 보여주기 좋음 | 특정 공개 데이터가 전동화 공정·개체 이력·설비 대안 실험을 모두 지원한다고 보장할 수 없음 | 공개 데이터 전반을 조사해 배제한 것은 아님. 실제 이력 데이터가 확보되면 외부 검증 모듈 추가 |
| 모의 공정 + 두 직무 모듈 | 같은 사례에서 품질·생산성·추적성·검증을 연결, 반복 실험 가능 | 현실성은 가정에 제한되고 생성식에 유리한 분석이 될 수 있음 | 현재 구현. 실제 데이터와 장비 검증을 후속 단계로 명시 |

### 왜 네 공정인가

체결→접합→밀봉검사→최종검사는 측정값, 품질 결과, 공정 시간, 대기의 관계를 설명할 수 있는 교육용 흐름입니다. 실제 제조 기업의 상세 공정을 복제한 구성이 아닙니다. 한 공정만 있으면 공정 간 대기와 병목 이동을 설명하기 어렵고, 공장 전체로 넓히면 혼자 검증할 수 있는 범위를 넘기 쉽습니다.

### 왜 로지스틱 회귀인가

수치형 특징 여섯 개로 시작할 수 있고, 표준화와 계수의 역할을 설명하고, JSON 계수만으로 경량 추론을 구현하기 쉽기 때문입니다. DNN이나 트리 모델보다 성능이 우수하다고 비교 실험한 것은 아닙니다. 현재 선택은 작은 기준 모델로 데이터·평가·배포 경로를 먼저 확인하기 위한 것입니다. 독립된 검증 데이터에서 비선형 모델의 이점이 확인되면 비교 대상으로 추가할 수 있습니다.

### 왜 시간순 분할인가

실제 활용의 기본 형태는 과거 데이터로 학습하고 이후 제품을 평가하는 것입니다. 그래서 일자 1–18은 학습, 19–24는 검증, 25–30은 시험으로 나눴습니다. 같은 일자가 서로 다른 분할에 섞이지 않게 했으며, 표준화와 입력 허용범위는 학습 데이터에서만 계산합니다. 모든 종류의 누수를 해결했다는 뜻은 아니고, 현재 데이터 구조에 맞춘 최소 방어입니다.

### 왜 개선안을 나눠 실험했는가

검사 셀 증설과 공정 편차 축소를 동시에 적용하면 어떤 변화가 어느 조치에서 왔는지 설명하기 어렵습니다. 따라서 기준·검사 셀 증설·편차 축소·결합의 네 대안을 비교했습니다. 동일 시드에서 사양과 난수를 공유해 대안 간 비교의 무작위 변동을 줄였습니다. 이것은 시뮬레이터 내부의 비교이며 현장의 인과 효과를 증명하지 않습니다.

## 3. 실제로 드러난 어려움과 대응

| 어려움 | 실제 확인 내용 | 구현한 대응 | 남은 문제 |
|---|---|---|---|
| 현실 데이터·설비 근거의 부재 | 이번 구현에 실제 제조 기업 데이터나 장비가 연결되지 않음 | 생성식·시드·가정 공개, 모의 데이터 표시 | 현장 일반화 미검증 |
| 데이터가 틀리면 분석도 틀림 | 중복·누락·시간 역전 등의 입력을 테스트에서 주입 | 잘못된 배치를 거부하고 제품·공정 키/순서/셀 점유 검증 | 실제 센서 결측·시간 동기화는 미검증 |
| 모델 점수와 운영 가능성이 다름 | 검증 검토율 51.4%, 시험 57.1%로 용량 가정 30% 초과 | Recall·Precision·검토율·혼동행렬을 함께 공개 | 용량 제약을 만족하는 정책은 아직 확보하지 못함 |
| 개선 효과를 구분하기 어려움 | 셀 증설만으로는 모형상 불량 생성식이 변하지 않음 | 네 대안의 생산성과 품질을 따로 비교 | 실제 편차 축소 방법·비용은 미확인 |
| 가벼운 추론과 학습 코드의 일치 | 학습 라이브러리와 별도 경량 코드가 존재 | 시험 입력에서 점수 일치 검증, 잘못된 입력에는 점수 대신 검토 상태 | Jetson의 지연·센서 통합 미검증 |
| 화면 자동검증 실패 | 자동화 도구로 range 입력에 fill을 사용했을 때 오류 발생 | 키보드 조작으로 테스트 방식을 수정, 이후 브라우저 검사 23개 통과 | 사용자가 장기간 사용한 운영 검증은 아님 |

여기서 중요한 것은 모든 어려움을 해결했다고 쓰지 않는 것입니다. 데이터 검증과 구현 일치성은 확인했지만 운영 용량과 현실 적용은 남아 있습니다. 브라우저 테스트 수정은 Codex의 실제 작업이며, 사용자의 독자적인 디버깅 경험으로 바꾸어 쓰지 않습니다.

## 4. 숫자가 알려주는 핵심 경험

시험 부품 1,080개 가운데 불합격은 317개였습니다. 모델은 그중 275개를 포착하고 42개를 놓쳤습니다. 추가 점검 후보 617개 중 실제 불합격은 275개이며, 나머지 342개는 정상 부품이었습니다.

- Recall = 275 / 317 = 86.8%.
- Precision = 275 / 617 = 44.6%.
- 검토율 = 617 / 1,080 = 57.1%.
- 용량 가정 30%라면 같은 규모에서 324개까지 검토할 수 있어, 293개가 초과합니다.

따라서 ‘불량을 86.8% 잡았다’만으로 도입을 제안하기는 어렵습니다. 실제 운영에서는 놓친 불량, 추가 점검의 부담, 검토 가능 인원을 함께 정의해야 합니다. 현재 30%는 실측한 인력 한계가 아닌 프로젝트의 가정입니다.

반례로, 모든 부품을 추가 점검하면 Recall은 100%가 되지만 검토율도 100%가 됩니다. Recall 하나만 최대화하는 것이 실용적인 해답은 아니라는 점을 보여줍니다.

공정 실험에서는 검사 셀을 늘린 대안과 편차를 줄인 대안을 구분했습니다. 결합 대안의 구간 내 완료량 차이 평균은 +35.73개였고 최초검사 합격률 차이는 +17.81%p였습니다. 이는 추가 셀과 편차 축소를 가정한 30쌍 모의 실험의 결과입니다. 실제 공장에서 달성한 생산량·품질 개선으로 쓰지 않습니다.

## 5. 경험정리 일기 — 1인칭 제안 초안

### 시작: 공부한 내용을 직무의 문제로 연결하고 싶었다

통계와 데이터 분석을 공부하고 온디바이스 AI 교육을 받으면서, 데이터를 정리하고 모델을 만드는 경험은 조금씩 쌓고 있었다. 제조 기업의 SDF 데이터 분석과 전동화 생산기술 직무를 염두에 두면서는 내가 배운 내용을 어떤 공정 문제와 연결할 수 있을지 정리할 필요가 있었다.

지금까지의 학습을 모델 종류나 사용 도구로 나열할 수는 있었지만, 분석 결과를 보고 누가 어떤 결정을 내릴 수 있는지까지 설명하는 부분은 더 연습하고 싶었다. 불량을 예측했다면 어떤 제품을 추가 점검해야 하는지, 점검할 수 있는 양은 충분한지, 설비를 늘리는 것과 공정 편차를 줄이는 것은 어떻게 다른지 묻는 프로젝트가 필요하다고 생각했다.

그래서 두 직무가 만나는 사례로 전동화 부품 조립을 가정했다. Codex의 도움을 받아 공정 데이터를 생성하고 검증하는 단계부터 품질 위험 분석과 공정 개선안 비교까지 이어지는 프로젝트 초안을 만들었다. 현재 결과물을 내 경험으로 발전시키려면 코드를 실행하고 가정을 바꾸며, 결과가 달라진 이유를 내가 설명할 수 있어야 한다는 과제가 남아 있다.

### 첫 번째 과제: 실제 데이터를 가진 것처럼 만들지 않기

이번 작업에는 실제 제조 기업의 공정 데이터가 연결되어 있지 않았다. 그렇다고 모의 데이터의 숫자와 화면만 그럴듯하게 꾸미면 직무 이해를 보여주는 근거가 약해질 수 있었다. 따라서 공정 조건과 불량 발생 방식을 코드로 공개하고, 모의 실험의 결과라는 점을 화면과 문서에 남겼다.

이 프로젝트에서 주장할 수 있는 범위는 가정한 문제를 일관되게 구현하고 재현 가능한 방식으로 분석했다는 것이다. 현장 품질을 개선했다거나 실제 설비 조건을 검증했다고 말할 수는 없다. 이러한 경계를 분명히 설명하는 것도 분석의 신뢰를 만드는 과정이라고 정리하고 싶다.

### 두 번째 과제: 모델 앞의 데이터를 검증하기

품질 위험을 계산하려면 한 부품의 측정값과 최종검사 결과가 정확히 연결되어야 한다. 중복된 제품 ID가 있거나 공정 순서가 뒤바뀌어도 그대로 분석하면, 모델 성능을 논하기 전에 데이터 자체를 믿기 어려워진다.

그래서 프로젝트에는 누락, 중복, 잘못된 시간, 동일 셀의 중복 점유 등을 확인하는 단계를 넣었다. 또한 최종검사 이후에 알 수 있는 결과와 완료시간은 예측 입력에서 제외하고, 과거 일자로 학습한 모델을 이후 일자에 평가하도록 구성했다. 분석을 시작하기 전에 데이터의 의미와 사용 가능한 시점을 먼저 설명하는 연습을 할 수 있는 구조다.

### 세 번째 과제: 좋은 포착률만으로 충분하지 않았다

실행 결과에서 가장 주목할 부분은 시험 불량 포착률 86.8%와 검토율 57.1%가 함께 나왔다는 점이었다. 숫자 하나만 보면 좋은 성과로 소개하기 쉬웠지만, 전체 부품의 절반 이상을 추가로 살펴봐야 한다는 뜻이기도 했다. 프로젝트에서 가정한 검토 용량은 30%였고, 검증 구간에서도 이미 이를 넘고 있었다.

그래서 결과를 정리할 때 포착률만 강조하지 않고, 놓친 불량과 정상 부품의 과잉 점검까지 함께 표시했다. 용량 초과를 해결했다고 쓰지도 않았다. 다음 단계에서는 실제 점검 가능량과 오판 비용을 정의하고, 그 조건 아래에서 어떤 정책이 가능한지 검증해야 한다. 기존 시험 데이터로 새 임계값을 고르면 새로운 성능 검증 자료가 필요하다는 점도 기억해야 한다.

이 사례를 통해 정리하고 싶은 배움은, 모델 평가가 숫자 비교를 넘어 작업량과 운영 조건에 대한 판단으로 이어져야 한다는 것이다.

### 네 번째 과제: 생산성과 품질의 변화를 구분하기

생산기술 모듈에서는 최종검사 셀을 늘리는 대안과 체결·접합 편차를 줄이는 대안을 나눠 비교했다. 검사 셀을 늘리는 것은 처리 능력과 대기에 영향을 주지만, 모형에서 이미 만들어진 부품의 불합격 여부를 바꾸지는 않는다. 반대로 편차 축소는 불합격 발생을 줄이도록 가정했지만 검사 설비의 수를 직접 늘리지는 않는다.

두 조치를 구분하고 같은 난수 조건에서 반복 실험한 이유는, 변화의 원인을 더 명확히 설명하기 위해서다. 결합 대안에서 더 나은 수치가 나와도 현실에서는 설비비, 작업자, 공간, 물류, 실제 편차 축소 방법을 다시 확인해야 한다. 지금 결과는 그런 후속 질문을 만드는 출발점으로 보는 것이 적절하다.

### 현재: AI의 결과물을 내가 설명할 수 있는 작업으로 바꾸기

이번 초안의 구현과 검증에는 Codex의 도움을 받았다. 따라서 결과물이 있다는 것과 내가 그 결과를 이해하고 있다는 것은 구분해야 한다. 앞으로는 한 부품의 데이터를 직접 따라가고, 임계값이나 공정 가정을 바꾸기 전에 예상 결과를 적은 뒤 실제 결과와 비교해 보고 싶다.

현재는 Windows CPU에서 경량 추론 코드를 확인한 상태다. 다음에는 Jetson Orin Nano에서 같은 입력을 재생하고, 입력 누락이나 학습 범위 밖 데이터가 들어왔을 때의 동작과 지연시간을 기록할 계획이다. 이후 여건이 되면 실제 수업 데이터나 비전 결과를 제품 ID에 연결하고, LLM은 검증된 분석 결과와 근거 파일을 설명하는 보조 단계부터 추가하고 싶다.

‘어제보다 더 나은 오늘’은 기능을 계속 붙이는 것뿐 아니라 어제 설명하지 못한 가정 하나, 확인하지 못한 결과 하나를 오늘 내 언어로 설명하고 검증하는 과정으로 실천하고 싶다.
