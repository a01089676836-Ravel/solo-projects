# 제조 이상탐지 Agent 프로젝트 경험 정리

이 글은 프로젝트를 처음부터 거창하게 기획했다는 식으로 꾸미지 않고, 내가 어떤 계기로 시작했고 대화와 구현을 거치면서 무엇을 확인했는지 정리한 것이다. 실제로 하지 않은 경험이나 electronics-manufacturer 내부 시스템을 구현했다는 내용은 넣지 않았다.

## 1. AX|PI 직무와 electronics-manufacturer DS 지원 이유를 구체화하다가 시작했다

제조 AI 교육 과정 On-device AI 과정에서 Jetson Nano를 이용한 프로젝트를 진행하며 데이터 분석과 Agentic AI 역할을 맡고 있었다. 이후 electronics-manufacturer DS부문의 AX|PI 직무가 실제로 어떤 일을 하는지, 그리고 여러 기업 중 왜 electronics-manufacturer DS에 지원하고 싶은지를 구체화하던 중 현재 참여 중인 프로젝트에도 이 관점을 반영해 볼 수 있지 않을까 생각했다.

처음부터 반도체나 MES를 구현하려던 것은 아니다. 현재 프로젝트에 AX|PI 관점의 요소를 적용해 보면서, 내가 이 직무와 electronics-manufacturer DS에 끌리는 근거를 자소서 작성과 프로젝트 고도화 방향에 대한 대화를 통해 찾아가 보려는 것이 출발점이었다. 실제 반도체 공장이나 설비 운전 데이터를 개인이 확보하기 어렵기 때문에, 현장을 재현한다고 주장하지 않고 현재 프로젝트와 가상의 환경, 공개 데이터를 이용해 확인할 수 있는 범위를 정했다.

처음의 질문은 “현재 프로젝트를 통해 AX|PI 직무와 electronics-manufacturer DS 지원 이유를 더 구체화할 수 있을까?”에 가까웠다.

## 2. 대화를 하면서 생각이 구체화된 부분

대화 초반에는 AI 모델과 Agent를 현재 온도 이상탐지 프로젝트에 붙일 수 있는지가 중심이었다. 이후 AX|PI의 업무 흐름을 구체적인 이름으로 살펴보면서 AI/ML, Data Pipeline, MES, Embedded/Linux, Digital Twin, 이상 감지, IT Infrastructure, 구축·운영이 따로 떨어진 기술 목록이 아니라 제조 시스템 안에서 연결되는 요소라는 설명에 공감하게 되었다.

특히 “데이터가 어떤 공정·설비·운전 상태에서 발생했는가”를 함께 봐야 한다는 관점이 현재 프로젝트에 적용할 수 있는지 확인해 보고 싶어졌다. 다만 이 관점이 처음부터 내 머릿속에 완성된 생각이었다고 소급해서 말하지는 않으려고 한다. AX|PI 직무와 electronics-manufacturer DS 지원 이유를 구체화하는 대화 속에서 이 관점이 더 선명해진 뒤 실제 코드에 적용해 확인한 것이다.

내가 지금 말할 수 있는 출발점과 결과는 다음처럼 구분된다.

| 구분 | 실제로 말할 수 있는 내용 |
|---|---|
| 시작점 | manufacturing AI program On-device AI 과정의 Jetson Nano 프로젝트에서 데이터 분석·Agentic AI 역할을 맡은 경험을 바탕으로, electronics-manufacturer DS AX|PI 직무와 왜 electronics-manufacturer DS인가를 구체화하던 과정 |
| 처음의 의도 | 현재 프로젝트에 AX|PI 관점을 적용해 보며, 자소서 작성과 고도화 방향 대화를 통해 직무·기업 지원 이유의 근거를 찾아보기 |
| 대화 후 구체화 | 센서 값만 보지 않고 공정·설비·운전 상태 문맥을 함께 보며, 데이터가 판단과 운영으로 이어지는 구조를 확인 |
| 현재의 결과 | 센서 입력부터 이상 판단, 안전 경계, 사건 기록, SOP/Agent 안내, 가상 MES 문맥, 공개 모드 기준선까지 연결한 작은 검증 구조 |

## 3. 가장 먼저 발견한 문제는 Agent가 아니라 정상 데이터였다

처음 온도 이상탐지 Agent를 실행했을 때 정상 데모 데이터가 지나치게 일정했다. 정상값의 분산이 거의 없으니 이상 점수와 임계값의 차이가 비현실적으로 커졌다. 이 문제를 보고 단순히 모델을 바꾸거나 LLM에게 설명을 더 잘 시키는 방식으로 해결하면 안 된다고 판단했다. 먼저 정상 기준선에 들어가는 데이터가 실제 정상 변동을 어느 정도 반영하는지 확인해야 했다.

그래서 세 가지 방향을 생각했다.

1. 정상 `runId`와 시간에 따른 변동을 넣되, 임의의 노이즈로 성능을 만들어내지 않는다.
2. 표준편차가 거의 0일 때 센서별 최소 변동폭과 median/MAD/IQR 기반 robust scaling을 사용하고, 변동 부족 자체를 한계로 기록한다.
3. 운전 모드가 다른 데이터를 하나의 전역 기준선으로만 묶지 않고, 모드별 기준선과 시간적인 지속 조건을 비교한다.

현재 코드에는 이 중 세 방향이 데모·벤치마크 수준으로 적용되어 있다. 합성 정상 데이터에는 결정적인 run/time 변동을 넣었고, 기준선에는 센서별 최소 변동폭과 robust scaling을 적용했다. 그래도 현재 정상 run 수가 적고 최소 변동폭이 적용되는 특징이 많으므로 현장 성능으로 해석하지 않는다.

## 4. 실제 MES가 없어서 MES-lite를 선택했다

실제 MES 계정이나 반도체 장비의 운전 데이터를 확보하지 못한 상태에서 전체 Eclipse BaSyx를 설치하는 것은 현재 질문에 비해 범위가 너무 커진다고 생각했다. BaSyx의 Digital Twin과 운전 모드 개념은 참고하되, 지금 확인하려는 것은 플랫폼 전체가 아니라 이상 이벤트에 Work Order, Lot, Operation, Equipment, 공정 운전 모드가 붙었을 때 문맥을 잃지 않는지였다.

그래서 `MES-lite`라는 최소 구조를 만들었다. 이것은 실제 MES가 아니라 다음을 검증하기 위한 가상 통합 경계다.

- 이벤트의 `equipmentId`와 MES 문맥의 `equipmentId`가 같은가
- 이벤트의 `runId`와 MES 문맥의 `runId`가 같은가
- `processModeId`와 장비 실행 방식인 `operationMode`를 서로 섞지 않는가
- `executionState`가 정해진 전이를 따르는가
- Agent가 문맥을 읽기만 하고 Work Order나 설비 제어를 임의로 바꾸지 않는가

이 판단으로 실제 BaSyx 설치·운영이나 실제 MES 연동을 했다고 말하지 않게 되었다. 로컬 실행에서는 `-VirtualMes` 옵션을 켜야만 가상 문맥이 붙도록 만들었다.

## 5. 공개 데이터는 반도체 데이터가 아니라 모드 기준선 검증용으로 분리했다

반도체 설비 데이터 대신 Tennessee Eastman 데이터를 사용한 이유는 반도체와 같아서가 아니다. 공개 저장소에서 Mode 1·3·4의 정상 시계열 파일을 확보할 수 있었고, 각 데이터에 `processModeId`와 시간 순서를 붙여 모드별 기준선을 비교할 수 있었기 때문이다.

Mode 1·3·4만 사용한 이유도 해당 저장소에서 이번 단계에 확보한 정상 파일의 범위가 그 세 모드였기 때문이다. 이 모드들이 반도체 공정을 의미한다고 판단한 것은 아니다. 따라서 원래 Jetson 센서 데이터와 섞지 않고, “다중 운전 모드 기준선 검증용 외부 벤치마크”로 별도 보관했다.

전역 기준선과 mode-aware 기준선을 정상 holdout으로 비교했을 때, 행 단위 mode-aware 오경보는 32/1,803건(1.775%), 전역 기준선은 0건이었다. 그러나 이 결과만으로 전역 기준선이 더 좋다고 결정하지 않았다. 현재는 정상 데이터만 있고 fault recall, onset 시점, 탐지 지연을 평가하지 못했기 때문이다. 전역 기준선이 모드 간 차이를 넓은 범위로 흡수했을 가능성도 있고, mode-aware 기준선이 Mode 1 후반 변동에 더 민감했을 가능성도 있었다.

그래서 한 번의 점수 초과를 바로 경보로 확정하지 않고 3행 연속 초과를 요구했다. 모드가 바뀐 직후에는 2행을 `MODE_TRANSITION`으로 보류했다. 그 결과 mode-aware temporal 결과는 10/1,803행(0.555%), 4개 경보 구간이었다. 이것은 짧은 튐을 보류하는 운영 규칙이 동작한 결과이지, 고장 탐지 성능이 향상되었다는 증거는 아니다.

## 6. Agent를 설비 제어자로 만들지 않았다

이 프로젝트에서 LLM을 붙인 목적은 안전 판단을 대신하게 하는 것이 아니라, 이미 구조화된 사건을 읽고 승인된 SOP에서 다음 확인 항목을 안내하게 하는 것이었다.

- 센서 입력 정규화·특징값·이상 점수는 코드가 계산한다.
- `NORMAL`, `ANOMALY`, `WARNING`, `EMERGENCY`와 LED·버저·서보 출력은 로컬 FSM이 결정한다.
- LLM에는 사건의 상태, 점수, threshold, evidence, 한계, MES 문맥을 사실로 전달한다.
- 원격 응답은 JSON Schema로 제한하고, 이벤트 evidence ID와 승인 SOP ID를 다시 확인한다.
- evidence나 SOP를 벗어나면 fallback으로 돌아간다.
- Agent plan에는 액추에이터 권한을 넣지 않고, 비정상 상황은 사람 확인을 요구한다.

할루시네이션 확인도 “모델이 절대 틀리지 않는다”는 방식으로 하지 않았다. 5개 시나리오를 실제 로컬 LLM에 실행해 evidence·SOP 참조·가상 MES 일치·액추에이터 분리를 확인했고, 존재하지 않는 `e99` evidence를 고르는 악의적 응답은 fallback으로 처리되는지 확인했다. 감사 결과는 모두 통과했지만, 이것은 현재 코드 경계와 참조 일치를 검증한 것이며 실제 현장 적합성이나 고장 원인을 증명한 것은 아니다.

## 7. 지금 만들어진 결과물

내가 만들려고 했던 결과물은 LLM이 설비를 마음대로 조작하는 시스템이 아니다. 다음 흐름이 끊기지 않는 작은 제조 이상 대응 구조를 만드는 것이었다.

```text
센서 관측값
  → 정상 기준선과 특징값
  → 이상 상태와 근거
  → 로컬 안전 FSM
  → 구조화된 사건
  → 가상 MES 문맥/API
  → 승인 SOP와 Agent 안내
  → 사람 확인·후속 추세 확인
```

2026-09-14 시점의 실행 증거는 `npm.cmd test` 45/45 PASS, `tools/check.ps1` 16/16 PASS, 로컬 llama.cpp/Qwen 검증 PASS, `npm.cmd run agent:audit` 전체 PASS였다. 이후 2026-09-21에 런타임 신뢰성 경계를 확장했고, 최신 `npm.cmd test`는 75/75 PASS다. 온도 데모는 정상 기준 threshold 1.8641, anomaly score 12.3217이며 상승률 9.00°C/분이라는 명시적 근거로 `ANOMALY`가 되었다.

## 8. AX|PI 지원과 연결해서 말할 수 있는 범위

이 프로젝트를 하면서 내가 관심을 갖게 된 것은 AI 모델 하나의 정확도만 높이는 일이 아니라, 데이터가 들어온 뒤 실제 판단과 운영에 사용되기까지의 연결을 직접 확인하는 일이었다. 현재 구현은 소형 센서 프로젝트의 범위이지만, 센서 데이터 수집·정규화·기준선·사건 구조·API·SOP·Agent·fallback을 한 흐름으로 묶어 보았다.

그래서 electronics-manufacturer DS AX|PI와 연결할 때는 “MES나 Digital Twin을 구현했다”고 말하기보다, “실제 제조 시스템을 구현해 본 것은 아니지만, 데이터가 어떤 설비·운전 상태에서 발생했는지를 문맥으로 보존하고, 분석 결과를 안전 경계와 점검 업무로 연결하는 작은 흐름을 구현해 보았다. 더 큰 제조 환경에서 이 연결 구조가 어떻게 설계·운영되는지 배우고 싶다”고 말하는 것이 정확하다.

처음부터 electronics-manufacturer에 맞춘 프로젝트를 설계한 것은 아니다. AX|PI 직무와 electronics-manufacturer DS 지원 이유를 구체화하는 과정에서 현재 프로젝트에 적용해 볼 수 있겠다고 생각했고, 데이터를 확인하고 코드를 고치는 과정에서 내가 어떤 업무 흐름에 더 관심이 있는지 구체화되었다. 지금의 결과물은 그 과정을 확인할 수 있게 만든 기록이라고 생각한다.

## 9. 아직 말하면 안 되는 것

- 실제 반도체 FAB 데이터로 검증했다고 말하면 안 된다.
- BaSyx 전체를 설치·운영했다고 말하면 안 된다.
- 실제 MES·Digital Twin·Cloud/Kubernetes/HPC를 구축했다고 말하면 안 된다.
- TEP 결과를 반도체 제조 성능으로 해석하면 안 된다.
- 정상 데이터만으로 fault recall이나 현장 오경보 성능을 주장하면 안 된다.
- LLM이 고장 원인을 확정하거나 설비를 직접 제어했다고 말하면 안 된다.

다음에 필요한 것은 기능을 더 크게 만드는 것보다, 독립적인 정상 run과 fault onset label을 확보해 mode-aware 기준선, 전역 기준선, persistence 규칙을 같은 기준으로 비교하는 것이다.

## 10. 2026-09-21 이후 신뢰성·런타임 보강

Astra를 기본 Agent 런타임으로 설정하고 OpenAI API endpoint·키 존재 여부를 별도로 확인했다. 다만 실제 smoke는 HTTP 429 `credit_balance_exhausted`로 생성 응답을 받지 못했으므로 Astra의 품질·지연·비용은 검증하지 않았다. 이 사실을 숨기지 않고 `liveVerified=false`로 기록했다.

대신 API 비용 없이 재현할 수 있는 경로를 추가했다. `agent:offline-run`은 외부 API와 로컬 LLM을 호출하지 않고 결정적 fallback, 근거, 사람 확인, 로컬 액추에이터 경계를 검증한다. `agent:harness`, `pipeline:check`, `reliability-compare`는 무근거 evidence·미승인 SOP·사람 승인 우회·자유 문장 주입을 회귀 검사한다. 느슨한 비교 정책은 악성 5건을 수용했지만 현재 어댑터는 5건 모두 거부·fallback 또는 자유 문장 제거로 처리했다.

따라서 최신 경험의 핵심은 “Astra가 답을 잘했다”가 아니라, 모델이 바뀌거나 API가 실패해도 로컬 안전 판단·근거 게이트·fallback·사람 승인·회복 재검증이 유지되도록 Agent의 권한과 실패 경계를 설계하고 검증한 것이다.
