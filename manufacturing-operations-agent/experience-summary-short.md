# 제조 이상탐지 Agent 프로젝트 경험 정리

제조 AI 교육 과정 On-device AI 과정에서 Jetson Nano 프로젝트를 진행하며 데이터 분석과 Agentic AI 역할을 맡고 있었다. 2년 뒤 electronics-manufacturer DS AX|PI에 지원하는 것을 염두에 두고 electronics-manufacturer DS부문의 AX|PI 직무가 실제로 어떤 일을 하는지, 그리고 왜 electronics-manufacturer DS인가를 구체화해 보던 중 현재 참여 중인 프로젝트에도 그 관점을 반영해 볼 수 있지 않을까 생각했다.

처음부터 반도체나 MES를 구현하려던 것은 아니다. 실제 반도체 공장이나 설비 운전 데이터를 개인이 확보하기 어렵기 때문에, 현장을 재현한다고 주장하지 않고 가상의 환경과 공개 데이터를 이용해 확인할 수 있는 범위를 정했다. 처음의 질문은 “현재 프로젝트에 AX|PI 관점을 적용해 볼 수 있을까?”에 가까웠다.

대화 초반에는 AI 모델과 Agent를 온도 이상탐지 프로젝트에 붙일 수 있는지가 중심이었다. 이후 AX|PI의 업무를 AI/ML, Data Pipeline, MES, Embedded/Linux, Digital Twin, 이상 감지, IT Infrastructure, 구축·운영이라는 구체적인 흐름으로 살펴보면서, 데이터가 어떤 공정·설비·운전 상태에서 발생했는지 함께 보고 분석 결과가 실제 운영으로 이어지는 구조에 관심을 갖게 되었다. 이 관점은 처음부터 완성되어 있던 생각이 아니라, AX|PI 직무와 electronics-manufacturer DS 지원 이유를 구체화하는 대화 속에서 더 선명해진 뒤 코드에 적용해 확인한 것이다.

처음 실행했을 때는 Agent보다 정상 데이터의 문제가 먼저 보였다. 정상 데모 데이터가 지나치게 일정해 분산이 거의 없었고, 그 결과 이상 점수와 임계값의 차이가 비현실적으로 커졌다. 이를 LLM의 설명 문제로 보지 않고 기준선과 데이터 문제로 판단했다. 그래서 정상 `runId`와 시간 변동을 추가하되 임의의 노이즈로 성능을 만들지 않았고, median/MAD/IQR 기반 robust scaling과 센서별 최소 변동폭을 적용했다. 변동이 부족한 특징은 숨기지 않고 `degenerateFeatures`와 한계로 남겼다.

실제 MES가 없기 때문에 전체 Eclipse BaSyx를 설치하지 않고, 현재 확인하려는 문맥만 `MES-lite`로 구현했다. Work Order, Lot, Operation, Equipment, `processModeId`, `operationMode`, `executionState`를 검증하고 event의 `equipmentId`와 `runId`가 맞을 때만 연결한다. BaSyx의 Digital Twin·운전 모드 개념은 참고했지만, 실제 BaSyx나 MES를 설치·운영했다고 말하지 않는다.

운전 모드 기준선은 Tennessee Eastman 데이터를 별도 벤치마크로 사용했다. Mode 1·3·4 정상 파일을 사용한 이유는 공개 저장소에서 이번 단계에 확보할 수 있었던 정상 파일의 범위가 그 세 모드였기 때문이다. 이 데이터는 화학공정 시뮬레이션이므로 반도체 데이터로 표현하지 않고, “다중 운전 모드 기준선 검증용 외부 벤치마크”로 분리했다.

정상 holdout에서 행 단위 mode-aware 기준선은 32/1,803건(1.775%)의 오경보, 전역 기준선은 0건이었다. 하지만 이 결과만으로 전역 기준선이 더 좋다고 결론내리지 않았다. fault recall, onset 시점, 탐지 지연을 측정할 fault 데이터가 없었고, 전역 기준선이 모드 차이를 넓은 범위로 흡수했을 가능성도 있었기 때문이다. 그래서 한 번의 초과를 바로 경보로 확정하지 않고 3행 연속 초과를 요구했으며, 모드 변경 직후 2행은 `MODE_TRANSITION`으로 보류했다. 그 결과 mode-aware temporal 결과는 10/1,803행(0.555%), 4개 경보 구간이었다. 이는 운영 보류 규칙의 동작 증거이지 fault 탐지 성능 향상의 증거는 아니다.

Agent의 역할도 제한했다. 센서 정규화, 특징값, 이상 점수, `NORMAL/ANOMALY/WARNING/EMERGENCY`, LED·버저·서보 출력은 로컬 코드와 FSM이 결정한다. LLM은 구조화된 사건을 읽고 승인된 SOP의 점검 항목을 안내한다. 원격 응답은 JSON Schema, event evidence ID, 승인 SOP ID로 다시 검증하며, 근거가 없거나 연결이 실패하면 결정적인 fallback으로 돌아간다. 가상 MES 문맥은 Agent의 사실 입력으로만 전달되고 설비 제어 권한은 주어지지 않는다.

할루시네이션 감사에서는 정상·온도 상승·모션 이상·작업자 경고·비상 5개 시나리오와 존재하지 않는 `e99` evidence를 선택하는 공격 응답을 확인했다. 현재 결과에서는 근거와 SOP 참조가 승인 범위 안에 있었고, Agent plan에 액추에이터 권한이 없었으며, 안전 출력은 로컬 FSM 결과와 같았다. 다만 이것은 현재 코드 경계와 참조 일치를 확인한 것이지 실제 현장 적합성이나 고장 원인을 증명한 것은 아니다.

현재 결과물은 LLM이 설비를 직접 조작하는 시스템이 아니다. 센서 관측값을 정상 기준선과 특징값으로 바꾸고, 이상 상태와 근거를 가진 사건을 만든 뒤, 가상 MES 문맥·API·승인 SOP·Agent 안내·사람 확인으로 이어지는 작은 제조 이상 대응 흐름을 구현한 것이다. 9월 14일 기준 `npm.cmd test` 45/45와 통합 검사 16/16을 확인했고, 9월 21일 신뢰성 경계 보강 후 최신 전체 테스트는 75/75 PASS다.

이 경험을 electronics-manufacturer DS AX|PI와 연결할 때는 실제 MES나 Digital Twin을 구현했다고 말하지 않는다. 대신 “현재 프로젝트에 AX|PI 관점을 적용할 수 있는지 궁금해서 시작했고, 데이터를 확인하고 코드를 고치는 과정에서 데이터가 어떤 설비·운전 상태에서 발생하는지, 분석 결과가 안전 판단과 점검 업무로 어떻게 이어지는지에 관심이 있다는 것을 구체화했다”고 설명할 수 있다. 다음에 필요한 것은 기능을 더 크게 만드는 것보다 독립적인 정상 run과 fault onset label을 확보해 기준선과 persistence 규칙을 비교하는 일이다.

최신 보강에서는 `gpt-6-astra` 런타임 설정과 API 키 분리를 확인했지만, 실제 Astra smoke는 크레딧 부족으로 성공하지 않았다. 대신 오프라인 fallback·근거 게이트·사람 승인·자동 재가동 금지를 회귀 검사했으며, 이는 Astra 품질 증명이 아니라 모델/API 실패에도 안전 경계를 유지하는 설계 검증이다.
