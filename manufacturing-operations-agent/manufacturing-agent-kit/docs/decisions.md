# 의사결정 기록

2026-09-07 현재 코드와 오늘의 요청을 근거로 작성. 과거 사용자 사고 과정을 소급한 기록이 아니다.

| 결정 | 대안과 선택 이유 | 증거·한계 |
|---|---|---|
| 기존 Node 기준선·읽기 API 유지 | Python 재작성보다 이미 검증한 경로 재사용. 현재 화면 기능에 Python 전환 필요 없음 | STATE.md, tests/events.test.mjs. Python 모델 확장 필요 시 재검토 |
| Opal은 실행·근거 검토 비서 | 탐지 모델 대체 대신 제공된 상태와 로그를 검토. 수치 계산은 기존 코드 | Opal 앱은 아직 생성·평가하지 않음 |
| 별도 SQLite 피드백 DB | 사건 DB 쓰기 권한 확대 대신 의견만 별도 저장 | 원래 사건은 읽기 전용 유지. pending_review 고정, 자동 학습 없음 |
| 의존성 없는 HTML 작업대 | 프레임워크 추가 전 목록→상세→피드백 한 흐름 검증 | 화면 복잡도·접근성 요구가 커지면 재검토 |
| LLM·파인튜닝 도입 보류 | SOP·반복 실패 증거 없이 모델 추가할 근거 없음 | 향후 검색/템플릿 대비 평가로 결정 |
| MES·운전 모드 문맥을 단계적으로 추가 | 실제 MES와 장비 운전 데이터를 확보하기 어렵기 때문에, 먼저 필요한 Work Order·Lot·공정·설비·운전모드 문맥을 `MES-lite`로 만들고 공개 다중 모드 데이터로 기준선의 모드 의존성을 검증 | 사용자가 대화 후 특히 “데이터가 어떤 공정·설비·운전 상태에서 발생했는가”라는 관점에 공감했다고 확인. 다만 이 관점이 처음부터 본인의 생각이었는지 대화를 통해 구체화된 것인지는 미확정으로 기록 |
| 단일 점수 초과를 즉시 이상으로 승격하지 않음 | `PENDING_ANOMALY`를 거쳐 3행 연속 초과 시 `ANOMALY`로 판정하고, `processModeId` 변경 직후 2행은 `MODE_TRANSITION`으로 보류 | TEP 정상 holdout에서 mode-aware 경보 행이 32건에서 10건으로 줄었지만 fault 데이터가 없어 성능 향상으로 결론내리지 않음. `src/tep-mode.mjs`, `reports/tep-mode-baseline.json` |

위 결정은 Codex가 이번 구현에서 내린 기술 판단이다. 사용자의 직접 판단과 의견은 별도 확인 후 기록한다.
