# 작게 비교하고 실제 판단을 기록하기

## 질문

같은 개발 과제에 결과만 요청하는 방식(A)과 목적·제약·완료 기준을 명시하는 방식(B)을 적용할 때 요구사항 충족, 오류, 수정 부담에 어떤 차이가 있는가?

이는 지시 방식 전체의 탐색적 비교다. 정보량도 달라지므로 개선 원인을 '의도' 하나의 효과로 단정하지 않는다. 의도 설명의 효과만 보려면 요구사항·자료·제약을 동일하게 두고 목적 설명 유무만 바꾸는 후속 비교를 한다.

## 비용을 제한하는 실행

- 첫 비교는 문서/설계 과제 하나로 한다. 자동으로 여러 모델·에이전트를 실행하지 않는다. 같은 모델과 설정을 사용하고 모델 비교는 별도 실험으로 분리한다.
- 같은 원본 코드·자료 스냅샷, 출력 범위, 실행 예산을 사용한다. 두 조건 모두 보안·데이터 누수 등 필수 제약을 제공한다. A를 일부러 망가뜨리거나 필수 안전 조건을 제거하지 않는다.
- 가능하면 독립 세션에서 실행해 B가 A의 답을 보지 못하게 한다. 불가능하면 이전 답의 영향 가능성을 기록한다. 반복 시 순서를 바꾸고, 1회씩이면 예비 사례라고 표시한다.
- 평가표는 결과 전에 고정한다. 기능 계약 충족/미충족, 근거 없는 주장 수, 발견된 결함, 총 처리 시간, 사용자 수정 횟수·시간, AI 수정 횟수를 기록한다. API 비용이나 작업 시간이 관측 불가능하면 미측정으로 남긴다.
- 자료가 없는 '정답'을 만들지 않는다. 자동 검사는 실제 동작에, 사람 검토는 적합성에 적용한다. 최종 코드 반영은 검토 후 선택하며 두 변경을 같은 원본에 덮어쓰지 않는다.

## 첫 후보: 제조 프로젝트의 SOP 검색 설계

기존 제품을 다시 만드는 대신, 다음 미구현 기능의 설계 초안을 비교한다. 실제 설비 매뉴얼이 없다는 조건과 교육용 자료 구분은 A/B 모두에 준다.

- 공통 입력: 현재 사건 JSON의 개발 표본, 기존 코드 계약, 제공된 근거 문서(없으면 없음), 원인 확정·설비 제어 금지, 고정 출력 길이.
- A: “이 프로젝트의 SOP 검색 기능 설계 초안을 작성해 줘.”
- B: 같은 요청에 “작업자가 어떤 문서에 근거한 제안인지 확인하고, 근거가 부족하면 판단을 보류할 수 있어야 한다”는 목적과 출처·보류·검색 실패 처리의 수락 기준을 추가한다.
- 평가표: 문서 식별/버전/구절 연결, 근거 없음 처리, 충돌 처리, 검색 실패 처리, 검증 가능한 테스트 제안. 이 표의 세부 기준을 미리 고정한다. B에만 알려준 기준의 효과가 포함됨을 보고한다.
- 결과를 읽기 전에 `reports/delegation/<experiment-id>/plan.md`를 작성한다. 실제 프롬프트와 결과는 A/B 별도 파일, 관찰은 `results.md`에 저장한다. 준비만 했다면 결과 파일을 성공 내용으로 채우지 않는다.
