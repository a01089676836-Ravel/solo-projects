# 의도를 정의하고 AI 업무를 검증하는 1인 프로젝트

## 사용자 동기와 경계

사용자는 통계·데이터 전공이며 개발 중심 코드에서 구조와 방법의 선택 이유를 판단하기 어렵다고 말했다. 제조 AI 교육 과정DX 관련 경험·채용설명회를 통해 AI 활용에서 목적과 의도, 결과 검증의 중요성을 느꼈고 이를 프로젝트에서 직접 경험하려 한다. 현장 설비 문제를 직접 겪었다거나 교육·근무 이력을 추가로 확인했다고 쓰지 않는다.

핵심은 코드 해설 서비스가 아니라 **목적을 정의해 AI에게 일을 맡기고, 결과를 판단·수정하는 경험**이다. 주제를 AI에게 추천받았다는 사실을 숨기지 않는다. 추천은 시작 계기이고, 이후 선택과 검증은 별도 증거로 남긴다. 학습 목적은 유효하며 가상의 현장 수요로 포장하지 않는다.

## 재개와 프로젝트 연결

- 기본 작업공간: `.`. 사용자가 다른 경로를 주면 우선한다.
- `STATE.md`, `AGENTS.md`, `docs/learning-charter.md`와 이번 작업에 필요한 코드·기록만 읽는다. 토큰 효율 선호를 유지한다.
- 제조 이상탐지 프로젝트는 학습을 적용하는 실제 개발 대상으로 활용한다. 제조 기능 구현은 기존 `manufacturing-anomaly-agent` 스킬의 데이터·근거·검증 조건을 따른다. 해당 스킬이 없으면 프로젝트의 `skill/manufacturing-anomaly-agent/SKILL.md`를 읽는다.
- 기존 기준선·SQLite·API·화면을 처음부터 다시 만들지 않는다. 기존 결과를 새 비교 실험의 결과로 소급하지 않는다.
- 스킬 준비 요청에는 지침과 실행 준비까지만 한다. 개발 재개 요청에는 다음 기능 하나에 이 흐름을 적용한다. 매번 전체 프로젝트를 비교 실험으로 반복하지 않는다.

## 한 작업의 실행 루프

1. **작업 선정:** 사용자가 결과를 직접 판단할 수 있는 다음 기능이나 검토 과제 하나를 고른다. 실용 목적과 학습 질문을 따로 쓴다.
2. **위임 카드 초안:** 사용자/해결할 일, 목적, 입력, 제약, 기대 산출물, 완료 기준, AI 역할, 사람이 결정할 항목을 작성한다. 사용자 발언·코드 사실·Codex 제안을 구분한다. 의도가 비어 있으면 제안임을 표시하고 가역적 준비를 계속한다.
3. **실행 또는 비교:** 일반 개발은 명확한 카드로 진행한다. instruction 전략 효과가 중요한 작업만 [experiment.md](references/experiment.md)에 따라 작은 비교를 한다.
4. **검증:** 코드의 동작은 테스트/실행으로, 근거의 적합성과 설명은 자료 대조로 검증한다. 설명이 설득력 있다는 이유만으로 결과를 신뢰하지 않는다.
5. **사람의 판단:** 목적·선택 이유·실패 조건·검증 근거를 사용자가 자신의 말로 짧게 설명하도록 제안한다. 직접 답을 받지 않았으면 이해 여부는 미평가다. 정형 인터뷰를 매 작업 강제하지 않는다.
6. **기록:** 기존 `docs/decisions.md`, `docs/ai-delegation.md`, `STATE.md`에 실제 선택, 거절·수정, 증거, 한계, 다음 행동을 남긴다. 인간의 수정과 AI의 수정을 구분한다.

도구·모델 선택은 현재 작업에서의 접근성, 편집·실행·검증 기능, 품질, 시간, 비용을 근거로 설명한다. 브랜드 우열을 만들어내지 않고 다른 도구를 써보지 않았으면 미비교로 둔다. 최신 제품 기능은 실제 구현 시 공식 확인한다.

## Opal 비서 역할

Opal은 **AI 업무 위임·검토 비서**로 설계한다. 목적/입력/완료 기준의 누락을 찾아 위임 카드 초안을 만들고, 실제 결과를 기준과 대조하고, 사람에게 남은 판단을 보여준다. 단순 진행 관리보다 위임과 검증을 중심에 둔다.

`사용자 요청·자료 → 사실/제안/누락 분리 → 위임 카드 → 외부 작업 결과를 사용자 입력으로 수신 → 기준별 검토 → 사람의 판단·인계 기록`

실제 앱 제작 요청에는 [opal.md](references/opal.md)를 읽는다. Opal이 로컬 Codex나 파일을 자동 실행·조회한다고 가정하지 않는다. 기본은 붙여 넣기이며 모델 학습과 앱 제작을 구분한다. 기존 프로젝트 Opal을 이 역할로 수정해 중복 앱 생성을 피한다.

## 성공 기준과 포트폴리오

- 제품: 선택한 기능이 사전에 정한 완료 기준을 충족한다.
- 학습: 사용자가 실제 선택 이유와 적용 한계를 설명하고 검증 근거를 제시할 수 있는지 확인한다. 대답을 대신 작성한 것은 학습 성과가 아니다.
- 탐구: 비교의 결과가 개선·동률·악화 중 무엇이든 보고한다. 소규모 사례를 AI 전반이나 현장 생산성으로 일반화하지 않는다.
- 설명: 시작 계기 → 확인하고 싶었던 질문 → 업무와 도구 선택 → 위임 방식 → 발견한 실패/한계 → 사람이 내린 판단 → 검증 결과 순서로 실제 기록에 연결한다.
- 제조 모델 성능, 비서 응답 품질, 사용자의 이해도를 별개로 보고한다. 파인튜닝·복잡한 Agent는 증거 있는 필요가 생길 때만 추가한다.
