# 구현·검증·포트폴리오

## 단계와 완료 근거

1. 데이터 적합성: 공식 출처·라이선스·해시·단위·분할 근거가 적힌 data card. 부적합하면 데이터 또는 목표를 바꾼다.
2. 탐지 기준선: 재실행 명령, 환경 lock, seed, 데이터/코드 버전, validation 임계값, 손대지 않은 test 결과. 단순 임계값과 후보 모델을 동일 분할에서 비교한다.
3. 수직 기능: 실제 데이터 한 사건을 SQL → API → 화면 → 피드백까지 연결. 오래된 데이터, 결측, 잘못된 ID, 중복 피드백을 테스트한다.
4. Agent: 템플릿/검색/Agent 비교와 실패 시 보류·fallback. 도구 실행 trace와 실제 사용량을 보관한다. API 키 없이 재현하는 mock 모드는 live 모드와 명확히 구분한다.
5. 사용자 평가: 정상·이상·불확실 사례의 판단 정답 기준을 먼저 정한다. 시나리오 공개부터 판단/다음 조치 선택까지 측정한다. 실제 작업자 미참여라면 대리 사용자 평가라고 표기한다.
6. 공개 준비: README, 아키텍처, data/model card, 성능표, 실패 사례, 짧은 데모, 재현 명령, 의사결정 기록. 공개 전 원본 데이터 재배포 조건과 비밀값 포함 여부를 확인한다.

## 평가 기준

모델은 PR-AUC(라벨이 있을 때), 고장 사건 단위 recall, 설비·일별 오경보, 탐지 지연/선행시간을 데이터가 지원하는 범위에서 보고한다. 사건 매칭 허용 구간, 중복 알림 묶기, 누락 정의와 분모를 고정한다. 점 단위 accuracy만으로 성과를 표현하지 않는다. 적은 사건 수에서는 사건 수와 불확실성을 함께 표시한다.

Agent는 근거 구절 정확성, 근거가 주장을 뒷받침하는 비율, 정보 부족/충돌 시 보류, 허구 센서/원인, 도구 실패 대응, p50/p95 지연 및 건당 비용을 평가한다. 같은 개발 사례에 프롬프트를 맞춘 뒤 그것을 최종 성능이라고 하지 않는다. `evals/scenarios.json`은 개발 회귀 사례이며 별도 보류 사례를 확보한다.

UX 초기 목표는 평가 시나리오의 80% 이상에서 올바른 판단과 다음 조치를 30초 안에 선택하는 것이다. 이 수치는 제안 목표이지 실측 성과가 아니다. 참가자 수, 시나리오 수, 오판, 판단 보류를 기록한다. API p95 목표는 실제 데이터/장치 조건을 보고 별도로 설정한다.

생산성 효과는 오경보 점검 비용과 미탐 비용을 여러 가정에서 비교한다. 예: 총비용 = 오경보 수×점검 비용 + 미탐 수×예상 손실 + 시스템 운영비. 실제 공장 비용이 없으면 민감도 분석/시뮬레이션으로 표기하고 절감 실적이라고 쓰지 않는다.

## 개발 하네스

작업 요청은 문제/입력/출력/실패 처리/수락 기준/검증 명령으로 작성한다. 한 번에 재현 가능한 기능을 완성하고 관련 테스트 후 상태를 갱신한다. 전역 Codex 설정, 권한 완화, 상시 작업은 필요하지 않다.

구현 이후 `tools/check.ps1` 뒤에 실제 테스트 명령을 연결하고 CI에도 동일 명령을 쓴다. 데이터 스키마·누수 경계·API 계약·중복 저장·Agent 근거와 보류·화면 주요 흐름을 검증한다. 빈 테스트나 mock 성공을 실데이터 성능으로 보고하지 않는다. 아직 구현하지 않은 단계는 skipped/pending으로 표시한다.

예시 요청: “현장 사용자가 설비 이상과 다음 확인 항목을 30초 안에 판단해야 한다. 현재 STATE.md를 읽고 사건 조회 API와 작업자 화면 한 흐름을 구현해줘. LLM 실패 시에도 센서 추세를 보여주고, 오래된 데이터와 중복 피드백을 검증해줘.”

## 면접 증거

각 주요 결정마다 문제 → 대안 → 선택 이유 → Codex에 맡긴 범위 → 생성 결과의 오류 → 직접 확인한 증거 → 한계를 기록한다. 아직 경험하지 않은 오류나 현장 인터뷰를 만들어내지 않는다. 기업별 연결은 지원 당시 채용 공고를 확인해 표현한다. 현장 관점에는 오경보·점검 흐름·사용성, AX 관점에는 도구 제한·근거·평가·운영 추적을 설명한다.
