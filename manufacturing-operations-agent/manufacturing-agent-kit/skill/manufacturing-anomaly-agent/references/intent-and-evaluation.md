# 의도 중심 프로젝트와 평가 하네스

## 설명회 맥락을 적용하는 방법

아래는 사용자가 전달한 IT 서비스 기업·electronics-manufacturer디스플레이 설명회 메모의 프로젝트 적용 기준이다. 회사의 공식 채용 정책이나 모든 면접관의 평가 기준으로 단정하지 않는다.

- AI를 업무를 맡기는 직원처럼 생각한다. 목적, 역할, 제공 정보, 산출물, 권한, 완료 기준을 정하고 사람이 결과를 검토한다.
- 결과물 완성과 함께 문제 선택 → 대안 비교 → 선택 이유 → AI 위임 → 사람의 판단 → 실패 → 수정 → 검증을 실제 증거로 설명한다. 이야기의 설득력을 위해 실패나 비교 실험을 창작하지 않는다.
- 학력은 무관하다고 단정하지 않는다. 프로젝트는 본인의 판단과 직무 역량을 보여주는 자료로 만든다.
- 자격증 수집을 기본 개발 단계로 넣지 않는다. 사용자 메모상 정보처리기사는 고려 대상이고 벤더 교육·자격은 업무 필요에 따른 선택이다. 특정 회사의 자격 존재·효력은 준비 요청 시 공식 확인한다.

## 착수와 매 작업의 기록

기존 프로젝트 문서를 재사용하고, 없으면 다음 산출물을 필요 시 만든다. 스킬 수정만으로 과거 의사결정을 소급 창작하지 않는다.

1. `docs/problem-brief.md`: 사용자, 반복되는 문제, 현재 처리 방식, 왜 AI가 필요한지, AI 없이 해결하는 대안, 데이터 제약, 완료 기준.
2. `docs/decisions.md`: 날짜 / 결정할 문제 / 후보 / 선택 / 선택 이유 / 예상 단점 / 확인한 증거 / 다시 검토할 조건 / 사람이 내린 판단. 아직 비교하지 않은 선택은 가설로 표시한다.
3. `docs/ai-delegation.md`: 맡긴 작업 / 의도 / 도구·모델·버전 / 입력과 범위 / 기대 결과 / 금지 행동 / 수락 기준 / 실제 결과 / 사람이 수정하거나 거절한 내용 / 증거 경로.
4. `STATE.md`: 실제 완료·검증·제약·다음 행동. 최종 포트폴리오는 위 기록과 실행 결과에 연결한다.

ChatGPT·Claude·Codex·Opal 선택은 브랜드의 고정 우열로 설명하지 않는다. 해당 작업의 파일·도구 접근, 편집 가능성, 결과 품질, 검증 편의, 비용, 지연, 데이터 취급 조건으로 판단한다. 단순 작업마다 모든 모델을 비교할 필요는 없다. 핵심 선택이 불확실하면 같은 입력과 평가 기준으로 이용 가능한 후보를 작게 비교하고, 미사용 후보는 미평가로 표시한다.

## 필요한 AI 비서와 파이프라인

기본 비서는 **프로젝트 실행·의사결정 증거 비서**다. 진행 계획뿐 아니라 선택 이유의 누락, 근거 없는 성능 주장, 사람이 확인해야 할 항목을 찾아준다. 현재 병목에 맞는 업무 하나부터 만든다.

`사용자가 제공한 상태·요청·증거 → 사실/제안/충돌 분리 → 요청별 작업 → 근거 대조 → 사람 검토용 결과 → 다음 세션 인계`

- 입력: 최신 STATE 요약, 당일 요청, 결정 메모, 실제 로그 발췌와 출처, 시간 제약. 공개·합성·비식별 자료만 기본 예제로 사용한다.
- 작업: 다음 행동 제안 / 실험 검토 / 의사결정 기록 초안 / 주장-증거 점검. 기록 초안은 사용자 확인 전 본인의 확정 판단으로 저장하지 않는다.
- 출력: 결과, 선택 이유, 근거 ID, 미확인 사항, 사람의 결정이 필요한 부분, 다음 행동과 완료 기준. 외부 파일을 실제 수정하지 않았다면 복사용 초안이라고 표시한다.

발전 단계는 현재 구현 상태에 맞춰 선택한다. 이미 있는 코드·API를 Opal 순서에 맞추려고 다시 만들지 않는다.

| 단계 | 목적 | 다음 단계로 갈 증거 |
|---|---|---|
| AI 없는 기준 방식 | 수동 체크리스트·검색의 시간과 오류 파악 | 동일 과제의 기준 기록 |
| Opal 작은 비서 | LLM을 업무 흐름에 연결하고 입출력·분기 설계 | 실제 앱 실행 결과와 실패 사례 |
| 코드·검색/API 연결 | 확인된 연동·재현성 병목 해결 | 동일 사례의 개선 결과와 통합 테스트 |
| Agent 동작 | 필요할 때 도구·경로를 선택하고 재시도 | 선택 경로·중단·실패 복구 실행 추적 |
| 선택적 모델 맞춤화 | 반복되는 업무 실패 개선 | 기준 방식 대비 독립 평가에서 효용 입증 |

Opal 앱을 만든 것을 LLM 자체 개발·학습으로 표현하지 않는다. 고정 순서 워크플로, 모델 주도 도구·경로 선택, 직접 구현한 실행 제어를 구분한다. Opal에도 Agent Mode가 있으므로 도구 이름만으로 agentic 경험 여부를 단정하지 않는다. 실제 계정 기능과 실행 추적으로 설명한다. 상세 제작은 [opal-assistant.md](opal-assistant.md)를 따른다.

## 평가 하네스: 같은 사례를 다시 실행하는 구조

하네스는 앱의 입력·출력·실행 기록을 모아 기준 방식과 변경 후 결과를 비교하는 장치다. 기존 `evals` 구조를 먼저 확인하고 별도 체계를 중복 생성하지 않는다. Opal 자동 실행 연동이 확인되지 않으면 UI에서 수동 실행하고 결과를 저장한다. 자동화했다고 주장하지 않는다.

- 사례 필드: `case_id`, `split`(개발/최종평가), `task`, `input`, `evidence`, `expected_behavior`, `forbidden_behavior`.
- 실행 필드: `run_id`, `case_id`, 앱/프롬프트/모델 버전, 실행 시각, 실제 출력, 가능한 도구 실행 추적, 소요 시간, 관측 가능한 비용, 평가 결과, 실패 이유, 사람의 수정. 측정할 수 없는 비용은 0이 아닌 미측정으로 둔다.
- 최소 사례: 정상 요청, 입력 부족, 상충하는 성능 주장, 오래된 상태, 문서 속 지시문, SOP 근거 없음, 도구 실패, 권한 밖 설비 제어 요청. 구현된 경로에 적용하고 미지원 경로는 미실행 사유를 기록한다.
- 비교: AI 없는 기준 방식과 비서 결과에 같은 과제를 주고 근거 연결 정확성, 없는 사실 생성, 필요한 판단 보류, 다음 행동의 실행 가능성, 사람의 수정 시간과 총 처리 시간을 비교한다. 합격 기준은 결과를 보기 전에 정한다.
- 완료 게이트: 평가 사례에서 완료·성능·출처 창작이나 설비 제어 실행은 실패다. 해당 실행을 숨기지 않고 수정 후 개발 사례로 재검증한다. 최종평가 사례를 보고 튜닝하면 더 이상 독립 평가라고 부르지 않는다.
- 코드 Agent에는 도구 허용 목록, 호출/시간/비용 상한, 제한된 재시도, 근거 부족 시 중단, 사람이 검토하는 출력을 구현하고 실행 추적을 확인한다. Opal에서 제어할 수 없는 항목은 한계로 남긴다.
- LLM 자기평가만으로 통과시키지 않는다. 형식·참조 존재 검사는 코드로, 근거의 의미와 제안의 적합성은 사람이 확인한다. 소규모 사례 통과를 현장 일반화로 확대하지 않는다.

## 자체 LLM: 보안과 업무 가속화를 분리해서 검증

설명회 메모의 목적은 **보안과 업무 가속화**다. 파인튜닝 자체가 보안을 보장하거나 사내 문서를 최신 상태로 검색하게 만드는 것은 아니다.

| 요구 | 우선 검토 | 증거 |
|---|---|---|
| 민감 정보 통제 | 배포 위치, 접근 권한, 외부 전송, 보관·학습 사용 조건, 로그 마스킹 | 데이터 흐름도와 실제 설정 |
| 사내 문서의 최신 근거 | 접근 통제된 검색/RAG | 출처 정확성·검색 실패·권한 검사 |
| 용어·형식·반복 작업 적합성 | 프롬프트·예시·출력 구조부터, 필요하면 파인튜닝 | 고정 평가에서 오류·수정 시간 비교 |
| 업무 가속화 | 사람의 확인·수정까지 포함한 전체 작업 개선 | 전후 총 처리 시간·오류·비용 |

파인튜닝은 필수가 아니다. 반복 실패, 사용 가능한 학습 데이터의 권리·품질, 분리된 평가 자료, 비용 대비 이점이 확인될 때 별도 실험으로 진행한다. 모델 학습, 사내/로컬 배포, RAG, Opal 연결은 각각 무엇을 실제 구현했는지 구분한다. 실제 기업 보안 인증이나 생산성 향상을 검증 없이 주장하지 않는다.

## 면접 산출물

실제 완료 후 문제·선택 이유·AI 위임·사람의 수정·전후 평가·남은 한계를 담은 짧은 사례 설명을 만든다. 원본 의사결정 기록, 실행 결과, 실패 사례, 재현 방법에 연결한다. 진행 중에는 미완료 범위가 드러나는 초안으로 작성한다.
