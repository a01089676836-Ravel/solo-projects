# 이 프로젝트를 왜, 어떻게 만들었는가

## 실무 질문과 학습 질문

실무 질문은 **“구매 업무의 어느 구간을 먼저 조사해야 하는가?”**입니다.

학습 질문은 **“어떤 원본 이벤트를 어떤 규칙으로 계산했기에 이 구간을 추천하는가, 그리고 어떤 정보가 추가되면 이 판단을 바꿔야 하는가?”**입니다.

결과만 보여주는 것을 피하기 위해 사용자가 요청한 `evidence-traceability` 스킬을 적용했습니다. 이 문서는 실제로 사용한 입력·선택 기준·실행·검증을 설명하며 모델의 내부 추론 과정을 재구성한 문서가 아닙니다.

## 전체 흐름

사용자 목표 → 공식 구매 로그 → 사례 단위 데이터 정리 → 비교 가능한 구매 유형·사례 선정 → 직접 전이와 시간 집계 → 조사 후보 선정 → 원본 사례 확인 → 개선 가정 계산 → 독립 SQL·자동 테스트 → 사람이 업무 조건을 확인하고 판단

## 1. 기존 프로젝트에서 무엇을 보완하는가

기존 PCB 검사는 이미지 모델 개발, 제조 Agent는 이상 대응, roadmap Copilot은 과제 우선순위·로드맵을 보여줍니다. 이번 프로젝트는 실제 업무 기록에서 문제 후보와 KPI 기준값을 산출하는 경험을 추가합니다.

## 2. 왜 이 데이터를 선택했는가

BPI Challenge 2019는 실제 기업의 구매 처리 기록이고, 공식 제공처에 출처·라이선스·사례 수·파일 MD5가 있습니다. 데이터 포털 웹 페이지는 도구에서 열리지 않았지만 공식 Figshare API에서 원본 위치와 메타데이터를 확인했습니다. 다른 개인의 분석 결과나 가공 데이터는 입력으로 사용하지 않았습니다.

원본 전체는 251,734개 구매 항목, 1,595,923개 이벤트입니다. 원본 파일을 약 729 MB 다운로드한 뒤 제공처 MD5와 대조했고 SHA-256도 남겼습니다. 사례 ID는 구매 문서와 항목의 조합입니다. 항목 수를 주문 문서 수라고 말하면 안 됩니다.

## 3. 왜 모든 구매를 한꺼번에 비교하지 않았는가

입고가 필요한 구매, 입고 없이 처리하는 구매, 위탁 구매는 기대하는 업무 흐름이 다릅니다. 우선 `3-way match, invoice before GR` 유형을 선택했습니다. 이 명칭은 허용되는 구매 방식이며 모든 사례에서 실제 송장이 입고보다 먼저 기록되었다는 뜻은 아닙니다.

또한 반복 입고·송장·지급은 정상적인 분할 처리일 수 있습니다. 첫 버전에서는 생성·입고·송장 접수·지급 기록이 각각 한 번 있는 사례를 골랐습니다. 취소·삭제, 시간 순서 모순, 동일 활동·동일 시각 중복 후보도 제외했습니다. 제외는 데이터가 잘못되었다는 판정이 아니라 비교 범위를 좁히는 규칙입니다.

그 결과 해당 유형 221,010건 중 160,642건을 비교했습니다. 모든 사례의 포함 여부와 제외 사유는 `reports/cohort-membership.json`에서 확인할 수 있습니다.

## 4. 어떻게 시간이 긴 구간을 계산했는가

사례별로 이벤트를 UTC 시간순으로 놓고 바로 이어지는 두 활동의 경과시간을 계산했습니다. 같은 시각이면 원본 순서를 유지합니다. 이는 실제 업무의 인과적 순서를 입증하지 않습니다.

각 구간에 대해 사례 수, 발생 수, 중앙값, P90, 누적 사례·일을 구했습니다. 30개 이상 사례에 나타나는 구간 중 누적 경과시간이 가장 큰 구간을 첫 조사 후보로 정했습니다. 드물지만 극단적으로 오래 걸린 사례 하나만 보고 추천하는 것을 줄이기 위한 기준입니다. 30은 이 프로젝트의 탐색 기준이며 통계적 유의성 기준은 아닙니다.

## 5. 무엇을 확인했는가

비교 코호트의 생성 → 지급 기록 중앙값은 76.70일, P90은 126.17일입니다. 가장 큰 조사 후보는 송장 접수 기록 → 지급 기록이었습니다.

화면에서 구간을 선택하면 경과시간이 긴 근거 사례를 최대 5개 볼 수 있습니다. 이들은 설명용 극단 사례이며 무작위 대표 표본이 아닙니다. 전체 지표는 코호트 전체로 계산했습니다.

## 6. 개선 가정과 실제 개선은 어떻게 다른가

선택 구간의 경과시간만 20% 줄이고 다른 구간은 유지하면 전체 코호트 중앙값은 69.29일입니다. 관측 기준과의 차이는 7.41일입니다.

이 결과는 산술적 민감도 분석입니다. 실제로 그만큼 줄일 수 있는지, 계약상 지급기한을 어기는지, 다른 업무에 부담이 생기는지 확인하지 않았습니다. 따라서 이력서에는 “처리시간 7.41일 단축”이라고 쓰면 안 됩니다. “구간 단축 가정에 따른 중앙값 변화와 한계를 계산했다”고 설명해야 합니다.

## 7. 어떻게 검증했는가

코호트를 Python으로 만들고, 별도 SQL 조건으로 다시 선정해 사례 ID 집합을 대조했습니다. 중앙값은 별도 통계 함수로 비교했습니다. 모든 인접 구간 시간의 합이 사례 전체 시간과 일치하는지도 확인했습니다. 보고서가 노출하는 근거 전이 990개는 데이터베이스의 이벤트 순번·활동·시간차와 모두 대조했습니다.

추가로 누락 지급, 분할 입고, 취소, 시간대, 동시각 이벤트, 시나리오 0%, 잘못된 원본 해시, API 입력, 경로 접근, 화면 검색·오류 상태를 자동 검사했습니다. 실제 테스트 로그는 `reports/test-results.txt`에 있습니다.

최초 실행에서는 연결 가능한 브라우저가 없어 시각 검수가 미완료였습니다. 이후 사용자의 명시적 요청으로 별도 Playwright Chrome 검증을 진행했습니다. 실제 렌더링·검색·사례 선택·0/10/20/30% 시나리오 변경과 오류 복구를 확인했고, 데스크톱·모바일 폭 캡처도 시각 검토했습니다. 실제 브라우저 검사는 10개, DOM 대역 검사는 7개를 통과했으며 두 검증을 별도 기록합니다. 자세한 내용은 `reports/browser/검증결과.md`에 있습니다.

## 판단을 바꿔야 하는 반례

지급까지 오래 걸리는 이유가 계약된 정상 지급조건이고 이미 그 조건대로 처리되고 있다면, 가장 긴 구간이어도 개선 우선순위는 낮아질 수 있습니다. 이 경우 예외 보류·불필요한 가격 수정 등 다른 구간의 변경 가능성과 비용을 확인해야 합니다.

## 직접 확인해 볼 질문

화면에서 사례 하나를 열고 다음을 설명해 보세요.

1. 이 사례가 비교 대상에 포함된 이유는 무엇인가?
2. 화면의 경과시간은 어떤 두 이벤트에서 계산되었는가?
3. 왜 그 시간을 전부 낭비라고 말할 수 없는가?
4. 개선 효과를 실제 성과로 말하려면 어떤 추가 데이터가 필요한가?

이 설명을 읽었다는 것만으로 학습이 검증되었다고 판단하지 않습니다. 직접 사례와 수치를 대조하는 것이 다음 확인입니다.
