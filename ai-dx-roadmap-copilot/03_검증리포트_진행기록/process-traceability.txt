4. 처음부터 끝까지 진행한 순서
============================================================

1) 직무 연결을 확인했다.
- 채용공고의 DT 업무 네 가지를 프로젝트 기능으로 매핑했다.
- 기존 제조설비 이상탐지 Agent와 중복되지 않도록 전략·기획·거버넌스 프로젝트로 분리했다.

2) 폴더를 분리했다.
- 기존 electronics-manufacturer 폴더 안에 넣지 않고 F: 루트에 별도 프로젝트를 만들었다.
- 작업은 소스 폴더에서 하고, 검증된 파일만 최종 F: 폴더에 동기화했다.

3) 결정론적 코어를 만들었다.
- 6개 항목을 1~5점으로 입력한다.
- 전략 적합도 25%, 사업 영향 25%, 실행 가능성 15%, 데이터 준비도 15%,
  시급성 10%, 거버넌스 준비도 10%를 적용한다.
- 기존 포트폴리오와 중복되는 후보는 신규 프로젝트 추천에서 제외한다.
- 같은 입력과 같은 루브릭이면 같은 점수가 나오도록 했다.

4) KPI와 로드맵을 추가했다.
- 결과 KPI와 선행 KPI를 분리했다.
- 기준값이 없으면 목표 숫자를 만들지 않고 baseline_required로 보류한다.
- 0~30일, 31~60일, 61~90일의 산출물과 사람 승인 지점을 만든다.

5) 사람이 결정하는 파일럿 서버를 만들었다.
- Node.js 내장 HTTP 서버와 로컬 JSON/JSONL 저장소를 사용했다.
- 실행·결정·KPI 기준값·감사 이력 API를 만들었다.
- tenantId와 workspaceId를 실행 기록에 보존했다.
- viewer는 조회만, reviewer/admin은 결정·기준값 등록이 가능하도록 했다.

6) 실제 사용 흐름을 추가했다.
- 웹에서 새 후보의 제목·문제·담당 조직·KPI·6개 점수를 입력한다.
- 공개자료 제목과 http(s) URL을 후보의 근거로 연결한다.
- 승인·반려·보류와 사유를 후보 결과에 표시한다.
- KPI 기준값과 측정 출처를 사람이 입력한다.

7) 신뢰성·보안을 보완했다.
- Idempotency-Key로 같은 실행 재시도를 중복 생성하지 않게 했다.
- 같은 키에 다른 입력을 보내면 409 충돌로 거부한다.
- 동시 재시도도 저장소 잠금 안에서 다시 검사한다.
- 빈 값·점수 범위·ID·텍스트 길이·URL 형식을 검증한다.
- JSON Content-Type, CSP, frame 차단, referrer 제한을 추가했다.
- 감사 이벤트에 이전 해시와 현재 해시를 연결하고 변조를 감지한다.
- production에서는 local-demo-token을 자동 설치하지 않도록 했다.

8) 운영 문서를 만들었다.
- npm.cmd run verify로 테스트·데모·코어 검사를 한 번에 실행한다.
- 로컬 실행·중지·백업·복구·실패 대응·상용 전환 조건을 runbook으로 남겼다.

9) 마지막으로 출처 라벨을 정정했다.
- 채용공고 출처 제목을 실제 페이지 제목인
  2026년 하반기 신입사원 공개채용_경영지원으로 맞췄다.
- DT는 제목에 임의로 붙이지 않고 scope에 채용공고 내 DT 직무 섹션이라고 기록했다.
- 공식 페이지 제목을 industrial-automation 인재채용 WHY industrial-automation 페이지로 좁혔다.
- 이 페이지는 DT 직무 세부 근거가 아니라 회사·인재채용 일반 맥락이라고 명시했다.

5. 고려한 대안과 선택한 이유
============================================================

A. Astra/LLM부터 연결하기 vs 외부 API 없는 결정론적 코어부터 만들기
- 선택: 결정론적 코어
- 이유: 토큰 비용 없이 실행할 수 있고, 점수·근거·보류 규칙을 재현할 수 있다.
- 의도: 모델이 그럴듯한 말을 하는지보다 의사결정 경계를 먼저 검증한다.
- 결과: Astra는 선택적 후속 어댑터로 남겼고 live 품질을 주장하지 않는다.

B. 단순 노트북/데모 vs 로컬 파일럿 제품 흐름
- 선택: 로컬 파일럿
- 이유: 후보 입력부터 승인·KPI·감사까지 실제 업무 흐름을 보여줄 수 있다.
- 의도: 모델 제작 경험뿐 아니라 DX 과제 운영과 거버넌스 역량을 보여준다.

C. electronics-manufacturer 폴더 안에 추가 vs F: 루트 별도 폴더
- 선택: F: 루트 별도 폴더
- 이유: 두 프로젝트의 목적과 코드를 섞으면 포트폴리오 메시지가 흐려진다.
- 의도: 제조설비 기술 프로젝트와 DX 과제 포트폴리오 프로젝트의 차이를 분명히 한다.

D. 실제 industrial-automation 내부 데이터처럼 구성 vs 합성 데이터로 명시
- 선택: 합성 데이터
- 이유: 내부 데이터 접근 권한이 없고, 실제 성과를 만들면 허위 주장이 된다.
- 의도: 검증 가능한 구조는 만들되 회사 내부 사실은 주장하지 않는다.

E. KPI 목표값 자동 생성 vs 기준값 측정 후 사람 검토
- 선택: baseline_required
- 이유: 기준값 없이 만든 목표는 숫자 형태의 할루시네이션이 될 수 있다.
- 의도: KPI를 성과 확정기가 아니라 측정·검토 질문으로 사용한다.

F. AI가 승인 상태 변경 vs 사람 승인 게이트
- 선택: 사람 승인 게이트
- 이유: 예산·담당자·운영 전환은 책임이 필요한 결정이다.
- 의도: Copilot은 제안하고 사람은 승인하도록 권한을 분리한다.

G. URL을 자동으로 가져와 내용까지 주장 vs URL 형식·근거 연결만 검증
- 선택: URL 형식·연결만 검증
- 이유: 자동 수집하면 최신성·권한·외부 데이터 전송 문제가 생긴다.
- 의도: 출처 존재를 확인하되, 원문을 읽었다고 과장하지 않는다.

H. 일반 감사 JSONL vs 해시 연결 감사 이력
- 선택: 해시 연결
- 이유: 로컬 파일이 수정됐을 때 조용한 변조를 감지할 수 있다.
- 의도: 감사 이력의 존재뿐 아니라 무결성까지 보여준다.

I. 실행 재시도마다 새 run 생성 vs Idempotency-Key
- 선택: Idempotency-Key
- 이유: 네트워크 재전송으로 같은 과제가 여러 번 기록되는 것을 막는다.
- 의도: 실제 API 사용 상황의 중복 생성 위험을 줄인다.

J. PostgreSQL/SSO를 즉시 도입 vs 파일 저장소 기반 파일럿
- 선택: 파일 저장소 기반 파일럿
- 이유: 외부 인프라·계정·배포 권한 없이 전체 흐름을 재현할 수 있다.
- 의도: 제품 계약과 검증을 먼저 만들고, 상용 단계에서 PostgreSQL·OIDC/SSO로 교체한다.

K. 해커톤 산출물과 코드 혼합 vs 신뢰성 원칙만 참고
- 선택: 현재 프로젝트에 필요한 신뢰성 원칙만 참고
- 이유: 해커톤 요구사항과 이 직무 프로젝트의 제품 목적은 다르다.
- 의도: 기존 프로젝트의 코드와 목적을 섞지 않고 회귀·검증 관점만 재사용한다.

8. 아직 주장하면 안 되는 것
============================================================

- industrial-automation 내부 데이터나 실제 KPI를 사용했다.
- industrial-automation에서 실제 성과가 발생했다.
- 이 점수가 회사의 공식 평가 기준이다.
- Top 3가 실제 채용·투자 우선순위다.
- Astra 모델 품질이 검증됐다.
- 현재 상태가 production 또는 commercial 서비스다.

현재는 상용화를 검토할 수 있는 포트폴리오용 local pilot candidate다.
상용 전환에는 PostgreSQL, OIDC/SSO, 실제 RBAC, 커넥터, PII 정책,
관측성, 자동 백업·복구, 실제 사용자 검증과 배포 검증이 필요하다.
