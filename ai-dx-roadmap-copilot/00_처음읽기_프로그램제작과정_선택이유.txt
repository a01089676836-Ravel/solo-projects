industrial-automation DT 1인 프로젝트
프로그램 제작 과정·대안 선택 이유·검증 결과 안내
기준일: 2026-09-22

이 파일은 프로젝트를 처음 보는 사람이
무엇을 만들었는지, 왜 이렇게 만들었는지, 어디까지 검증했는지 빠르게 이해하기 위한 안내서다.
더 긴 원본 기록은 03_검증리포트_진행기록/process-traceability.txt에 보존되어 있다.

============================================================
1. 이 프로그램은 무엇인가
============================================================

여러 AI·DX 과제를 입력하면 다음 과정을 도와주는 로컬 파일럿이다.

1) 과제의 문제·담당 조직·KPI·데이터 준비도 등을 입력한다.
2) 정해진 기준으로 과제를 점수화하고 우선순위를 비교한다.
3) 상위 과제에 대해 KPI 초안과 30·60·90일 로드맵을 제안한다.
4) 기준값이 없으면 목표 숫자를 임의로 만들지 않고 측정을 요청한다.
5) 최종 승인·반려·보류는 사람이 하고, 이유와 이력을 저장한다.

즉, AI가 결정을 대신하는 프로그램이 아니라
AI의 도움으로 DX 과제를 더 근거 있게 판단하는 프로그램이다.

============================================================
2. 처음 시작한 이유
============================================================

기존의 AI·제조 경험을 DX 기획과 거버넌스 영역으로 확장하기 위해,
AI 기술을 만드는 것에 그치지 않고 문제를 과제로 정의하고
조직·프로세스·성과관리와 연결하는 DX 기획 역량까지 확장하고 싶었다.

industrial-automation DT 직무 공고를 확인하면서 모델 개발만으로는 부족하다고 느꼈다.
전사 DX 전략, 혁신 과제 발굴, 업무 프로세스 최적화와 거버넌스까지
연결하는 경험을 하나의 1인 프로젝트로 만들어 보고 싶었다.

============================================================
3. 처음부터 끝까지 만든 과정
============================================================

1) 직무와 프로젝트 방향 확인
채용공고의 DT 업무인 DX 전략·로드맵, AI/DX 혁신 과제 발굴·기획,
업무 프로세스 최적화·거버넌스, AI/DX 트렌드·벤치마킹을 확인했다.
그 결과 단순 모델 개발보다 과제 발굴과 실행계획을 다루는 프로젝트를 선택했다.

2) 프로젝트 후보 비교
여러 후보 중 AI·DX 과제 발굴·우선순위·로드맵 Copilot을 선택했다.
여러 과제를 비교하고, 왜 이 과제를 먼저 해야 하는지 설명할 수 있기 때문이다.
KPI Copilot은 보안 기능이 아니라 과제 실행 뒤 무엇을 측정할지 정리하는 기능이다.

3) 상용화 관점 설정
단순히 경험을 남기는 데서 끝내지 않고 실제 업무에 사용할 수 있는 수준을 목표로 했다.
다만 industrial-automation 내부 데이터와 운영환경은 없으므로 실제 상용 서비스라고 주장하지 않고,
상용 전환을 검토할 수 있는 로컬 파일럿으로 범위를 정했다.

4) 기존 프로젝트와 폴더 분리
electronics-manufacturer AX·PI 프로젝트와 목적과 메시지가 다르므로 F: 드라이브의 별도 프로젝트로 분리했다.
기존 프로젝트는 제조·AX·PI 흐름이고, 이번 프로젝트는 DX 과제 기획과 거버넌스 흐름이다.

5) 합성 데이터와 근거 범위 설정
실제 회사 내부 데이터와 성과를 사용할 수 없으므로 후보 과제·점수·KPI는 합성 예시로 만들었다.
채용공고의 실제 제목과 DT 직무 범위를 분리하고, 일반 인재채용 페이지는
DT 직무의 직접 근거가 아니라 회사·채용의 일반 참고자료라고 표시했다.

6) 결정론적 코어 구현
Astra나 외부 API를 먼저 연결하지 않고, 같은 입력에 같은 결과가 나오는 구조를 먼저 만들었다.
전략 적합도, 사업 영향, 실행 가능성, 데이터 준비도, 시급성, 거버넌스 준비도를 점수화했다.
기존 포트폴리오와 중복되는 후보는 신규 프로젝트 추천에서 제외했다.

7) KPI와 로드맵 구현
결과 KPI와 선행 KPI를 나누고, 기준값이 없으면 baseline_required로 보류했다.
이를 통해 기준 없는 목표 숫자를 자동으로 만들어 내는 문제를 막았다.
0~30일, 31~60일, 61~90일의 산출물과 사람 승인 지점을 표시했다.

8) 사람이 결정하는 파일럿 흐름 구현
후보 입력, 점수 계산, 결과 확인, 승인·반려·보류, 사유 기록, KPI 기준값 입력을 연결했다.
AI는 review_required 상태의 초안을 만들 수 있지만 approved로 직접 바꿀 수 없다.

9) 신뢰성·보안 경계 보완
중복 실행을 막는 Idempotency-Key, 역할별 권한, 입력값·URL 검증,
감사 이력, 감사 이벤트 해시 연결과 변조 감지, 웹 보안 헤더를 추가했다.

10) 검증과 문서화
테스트·데모·코어 점검을 npm.cmd run verify로 묶고,
운영·백업·복구·상용 전환 조건과 제작 과정을 문서로 남겼다.

============================================================
4. 대안 중 이 방식을 선택한 이유
============================================================

A. Astra/LLM부터 연결하기 vs 결정론적 코어부터 만들기
선택: 결정론적 코어
이유: 토큰 비용 없이 실행할 수 있고 점수·근거·보류 규칙을 재현할 수 있다.
의도: 모델이 그럴듯하게 말하는지보다 의사결정 경계를 먼저 검증한다.
Astra는 필요할 때 붙일 수 있는 별도 어댑터로 남겼다.

B. 단순 노트북·데모 vs 로컬 파일럿
선택: 로컬 파일럿
이유: 후보 입력부터 승인·KPI·감사까지 실제 업무 흐름을 보여줄 수 있다.
의도: 모델 제작뿐 아니라 DX 과제 운영과 거버넌스 역량을 보여준다.

C. electronics-manufacturer 폴더 안에 추가 vs F: 드라이브에 별도 생성
선택: 별도 생성
이유: 두 프로젝트의 목적과 코드가 섞이면 포트폴리오 메시지가 흐려진다.
의도: 제조 기술 프로젝트와 DX 기획 프로젝트의 차이를 분명히 한다.

D. 실제 산업 자동화 기업 데이터처럼 구성 vs 합성 데이터로 명시
선택: 합성 데이터
이유: 내부 데이터 접근권한이 없고 실제 성과를 주장하면 허위가 된다.
의도: 검증 가능한 구조는 만들되 회사 내부 사실은 주장하지 않는다.

E. KPI 목표값 자동 생성 vs 기준값 측정 후 사람 검토
선택: baseline_required
이유: 기준값 없는 목표는 숫자 형태의 할루시네이션이 될 수 있다.
의도: KPI를 성과 확정기가 아니라 측정과 검토를 위한 질문으로 사용한다.

F. AI가 승인 상태 변경 vs 사람 승인 게이트
선택: 사람 승인 게이트
이유: 예산·담당자·운영 전환은 책임이 필요한 결정이다.
의도: Copilot은 제안하고 사람은 승인하도록 권한을 분리한다.

G. URL 내용을 자동 수집해 주장 vs 제목·URL 형식만 검증
선택: 제목·URL 형식과 근거 연결만 검증
이유: 자동 수집은 최신성·권한·외부 데이터 전송 문제가 생길 수 있다.
의도: 출처가 있다는 사실과 원문을 실제로 읽었다는 주장을 구분한다.

H. 일반 감사 JSONL vs 해시 연결 감사 이력
선택: 해시 연결
이유: 로컬 파일이 수정됐을 때 조용한 변조를 감지할 수 있다.
의도: 감사 이력의 존재뿐 아니라 무결성까지 확인한다.

I. 재시도마다 새 실행 생성 vs Idempotency-Key
선택: Idempotency-Key
이유: 네트워크 재전송으로 같은 과제가 여러 번 기록되는 것을 막는다.
의도: 실제 API 사용 상황의 중복 생성 위험을 줄인다.

J. PostgreSQL·SSO 즉시 도입 vs 파일 저장소 파일럿
선택: 파일 저장소 파일럿
이유: 외부 인프라·계정·배포 권한 없이 전체 흐름을 재현할 수 있다.
의도: 제품 계약과 검증을 먼저 만들고, 상용 단계에서 교체한다.

K. 기존 해커톤 코드 재사용 vs 신뢰성 원칙만 참고
선택: 신뢰성 원칙만 참고
이유: 해커톤과 이번 프로젝트의 목적이 다르다.
의도: 코드를 섞지 않고 회귀·검증 관점만 가져온다.

============================================================
5. 내가 판단한 부분과 AI의 역할
============================================================

AI는 후보 아이디어, 구조, 코드 작성과 수정에 도움을 주었다.
하지만 어떤 직무를 연결할지, 상용화를 목표로 할지, 폴더를 분리할지,
Astra를 바로 사용할지, 실제 사실과 합성 예시를 어떻게 구분할지는
내가 계속 질문하고 확인하면서 결정했다.

특히 결과를 그대로 믿지 않고 출처 제목, DT 범위, 내부 데이터 사용 여부,
외부 API 호출 여부와 테스트 결과를 다시 확인했다.

============================================================
6. 검증 결과와 현재 한계
============================================================

- 테스트 23/23 통과
- 데모와 코어 점검 통과
- externalApiCalled=false
- 동일 입력 재실행·권한·테넌트·감사 무결성 검증
- 실제 industrial-automation 내부 데이터·조직 KPI·성과는 사용하지 않음
- Astra 실시간 연결과 생성 품질은 검증하지 않음
- 현재는 상용 서비스가 아니라 로컬 파일럿 제품 후보임

실제 상용화 단계에서는 실제 데이터, PostgreSQL, OIDC/SSO, 운영 RBAC,
데이터 커넥터, 배포·관측성·백업·복구 검증이 추가로 필요하다.
이는 현재 프로젝트의 누락이라기보다 다음 단계의 별도 작업이다.
